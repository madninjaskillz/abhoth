The router

abhoth router is an OpenAI-compatible gateway that lives in the same binary. Put it in front of your inference engines, and every client gets one URL and one model list.

New, and still on trial. The router was built to replace a LiteLLM plus nginx setup in front of a two-GPU inference server, and it's being shadow-tested against that setup. It works, but expect the configuration to change, and expect these docs to grow.

Why a router

With more than one engine, or more than one GPU, someone has to decide where each request goes. A generic proxy round-robins requests. That breaks prefix caches, lets a sub-agent take the lane the Lead needs, and passes every engine's quirks on to your clients. The router knows about coding agents:

  • Names: a model name can mean the whole pool, one card (-a, -b, falling back to the other card if theirs is offline), a catalog model, or an on-demand model that gets switched in.
  • Slot leases: Abhoth leases a slot for the Lead and each sub-agent. The router places leased requests on the lease's card and counts unleased traffic against the free lanes.
  • Lead priority: the Lead never queues, and one lane on its card can be kept free for it. Agents and other traffic wait their turn instead of getting a 429 from the engine.
  • Session affinity: requests with the same prompt_cache_key (or session header) stick to one card by rendezvous hashing, so its prefix cache keeps hitting.
  • Per-engine fixes: it clamps reasoning_effort to what the engine supports, translates "thinking off", drops parameters an engine would reject, and adds each engine's API key from a file.
  • Failover: one retry on another eligible upstream after a connect error, a timeout, a 502 or a 503, and only before the first byte is sent. A failing upstream cools down for 10 seconds.
  • Visibility: Prometheus metrics, a JSON status, and a JSONL request log with no request bodies.

Run it

abhoth router --config router.json --port 8020
abhoth router check --config router.json          # validate a config

Then point clients at http://<host>:8020/v1. In Abhoth, set it as lmStudio.baseUrl. Abhoth sees a gateway with several models, and leaves the router's /health alone.

Coming from LiteLLM

If you already run LiteLLM, generate the router's config from it:

abhoth router import-litellm --litellm config.yaml --lb nginx.conf \
  --key-file /run/secrets/engine-key --out router.json [--watch 10]

With --watch, it regenerates the config when the LiteLLM config changes and the router reloads it without dropping requests. That's how a shadow run follows your layout.

Placement

Placement is off by default, so the router behaves like a plain gateway until you turn it on:

{
  "placement": {
    "leaseAware": true,
    "admission": true,
    "affinity": true,
    "leadReserve": 1,
    "queueSeconds": 300
  }
}

A request is placed by its lease first, then by session affinity, then on the least-loaded card.

Endpoints

EndpointWhat
POST /v1/chat/completionsStreaming (passed through chunk by chunk) and non-streaming.
GET /v1/models, GET /v1/model/infoThe model list, and per-model details (never keys).
GET /health, /health/livelinessLiveness. These never call a model.
GET /metrics, GET /statusPrometheus text, and a JSON status for dashboards.
POST /admin/cards/<X>/drainStop new requests to a card before you switch it. Loopback or admin key only.

Responses carry x-served-model, x-abhoth-card and x-abhoth-upstream, so you can see where a request went.

What it doesn't do

There are no cloud-provider adapters, spend tracking, virtual keys or admin UI, and no embeddings, images or audio. It routes chat completions to engines you run. If you need the rest, put LiteLLM behind the router as one more upstream.
